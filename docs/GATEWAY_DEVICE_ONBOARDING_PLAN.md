# Branch Gateway and Device Onboarding Plan

**Status:** Approved flow; implementation blueprint, not a record of completed integration.

**Product authority:** [PRD](PRD.md), especially [architecture](PRD.md#5-architecture), [access and branches](PRD.md#61-access-and-branches), [telemetry ingestion](PRD.md#62-telemetry-ingestion), [fleet management](PRD.md#63-fleet-management), and [boundary contracts](PRD.md#7-boundary-contracts-and-compatibility).
**First assessed deployment:** One physical Pi 5, one physical LPG/environment node and weighing station, MQTT machine simulators, and a second branch with a separate simulated gateway identity. Live vendor machines are conditional on verified protocol evidence.

This document turns the PRD's `access-and-branches`, `telemetry-ingestion`, `fleet-management`, and `fuel-and-environment` requirements into an ordered implementation plan. Requirement IDs and acceptance targets remain in the PRD. No schema, API, Pi service, or screen described as **planned** below should be treated as deployed.

## 1. Intended operator and data flow

1. The owner completes details/location, primary manager and review. The existing idempotent branch creation commits one branch and its manager assignment, returns its ID, and leaves service closed with hardware setup incomplete. The next screen is that saved branch's hardware setup; pairing can be skipped and resumed without recreating the branch.
2. In hardware setup, the owner requests a short-lived, single-use pairing code. If replacing a gateway, the owner explicitly selects the old gateway for cutover. The owner opens the Pi dashboard separately from a phone or laptop on the same branch LAN; the cloud browser does not call the Pi.
3. The installer enters the code in the protected local Pi dashboard. Its server process generates or reuses a durable gateway UUID and secret, then redeems the code with FastAPI over verified outbound HTTPS. FastAPI records a **redeemed, awaiting owner confirmation** claim and returns a short verification fingerprint for display on the Pi; the cloud setup screen polls FastAPI for the same fingerprint. The installer and owner compare both screens, then the owner explicitly confirms in SpinSense. Only this confirmation activates the binding. A lost response can be checked or retried with the same identity and secret without creating another gateway.
4. The installer provisions a unique local MQTT credential and permitted topic for each project-owned ESP32 or simulator, then points it at the Pi's broker. The Pi's Mosquitto broker receives authenticated MQTT messages. The edge service validates the source ID in the permitted topic and payload, records observations in MariaDB before cloud delivery, and discovers previously unknown cloud devices. Broker connection alone is not proof of a valid sensor reading.
5. A new machine simulator or physical LPG node appears as a **pending discovery** in the branch. The owner confirms the actual identity and selects its type and label. For a machine, the owner also records capacity and only verified capabilities; for the LPG node, the owner maps its available sensors and commissioned cylinder positions. An approved asset remains separately marked `physical`, `simulated`, or `vendor`.
6. The Pi receives the approved registry through an authenticated configuration read. Subsequent valid observations synchronize through FastAPI into Supabase PostgreSQL. Authorized branch screens read persisted projections through FastAPI. Pending/unidentified observations cannot populate operational cards, availability, or physical incident state.
7. Branch setup distinguishes saved/unpaired, code issued, redeemed/awaiting confirmation, paired, pending device approval, connected, stale, offline, expired/rejected, and service unavailable. Code redemption is not proof of an active gateway, MQTT connection is not proof of a valid observation, and branch creation is not a command to open service. Historical records retain their original gateway/device/branch association after replacement.

```text
Owner/Next.js --Supabase session--> FastAPI --transaction--> Supabase PostgreSQL
         create branch; issue/confirm claim |          branch/gateway/device registry
Pi dashboard --local code entry--> Pi server --one-time HTTPS claim--> FastAPI
Owner/Next.js --poll claim status/fingerprint--> FastAPI
ESP32 + simulator --MQTT--> Mosquitto --Pi ingestion--> MariaDB
Pi sync --authenticated outbound HTTPS batches--> FastAPI --REST--> Next.js
```

**Why this boundary:** A branch UUID in an MQTT topic, request body, or `X-Branch-ID` header is a claim made by a sender. Only the active credential's database-backed gateway binding determines the cloud organization and branch. Local MQTT remains private to the branch; the Pi does not need a cloud MQTT broker or inbound internet access. The Pi dashboard and cloud app run in separate browser tabs; cloud status comes from FastAPI, avoiding a cross-origin HTTPS-to-local-HTTP dependency and [mixed-content constraints](https://developer.mozilla.org/en-US/docs/Web/Security/Mixed_content). The browser never receives the gateway secret or Supabase administrative credentials. WebSockets are optional later for screen delivery; they do not replace durable ingestion.

## 3. Identities, trust, and lifecycle

| Identity/state | Contract |
|---|---|
| Organization/branch | Existing Supabase UUIDs. A Pi is bound to exactly one existing active branch in one active organization; a branch has at most one active gateway. The simulated second branch gets a distinct gateway ID and secret even if run on the same computer. |
| Gateway | Pi-generated UUID and 256-bit random bearer secret, stored in a local file readable only by the dedicated service account/root; cloud stores a keyed/hash verifier, never the plaintext. No Supabase key is installed on the Pi. Gateway status is `awaiting_confirmation`, `active`, `replaced`, or `revoked`, with creation, last-contact, cutover, and revocation history. A pending gateway cannot sync observations, receive commands or establish healthy state. |
| Pairing claim | Owner-issued random 12-character base32 code, valid for 10 minutes and one branch/replacement request. Store only a hash; cap failed redemption attempts at five per claim and rate-limit by source. Redemption consumes the code and creates one pending binding plus a short, server-generated verification fingerprint shown on both dashboards. The fingerprint is a visual comparison cue, not a credential. Owner confirmation must occur within 10 minutes of redemption or the pending binding expires. A lost code may be replaced by explicitly cancelling its unconfirmed claim and issuing a new one. Expiry, cancellation, replay, closed organization, wrong branch/replacement target or conflicting gateway identity must not activate it. Do not log or persist the displayed plaintext code after issuance. |
| Device | Stable project-owned MQTT topic/source ID, constrained by a locally provisioned client credential and Mosquitto topic permission, then bound to one gateway and branch after cloud approval. A normal subscriber sees the topic/payload, not the publisher's broker username; it must not pretend otherwise. A unique registration prevents the same physical/source identity from being active in two branches. Type is `lpg_edge_node`, `washer`, `dryer`, or `washer_dryer`; source kind is `physical`, `simulated`, or `vendor`. Claimed payload fields do not override the registered type/branch. |
| Discovery | `pending`, `approved`, `rejected`, or `retired`, with first/last seen times and approval actor/time. Repeated samples update one candidate, not create repeated cards. A candidate must have an attributable client/source identity; unknown or unauthenticated publishers are rejected or quarantined locally. |
| Observation | Stable `record_id` UUID plus local increasing ID, gateway ID, registered device ID, boot/session ID and source sequence when available, gateway ordering/receipt time, source time or declared uncertainty, units, quality, and source kind. Cloud also records receipt time. `(gateway_id, record_id)` is unique; foreign collisions are conflicts, never successful duplicate acknowledgements. |

The Pi first stores a generated gateway identity/secret securely, then claims. An uncertain response is resolved by a credential-authenticated claim-status read or an idempotent retry of the same identity and secret; never generate a new identity merely because a response timed out. The owner compares the fingerprint displayed by the local Pi and cloud setup screens before confirming. A mismatch or unavailable Pi blocks confirmation; expiry releases the pending claim for a new code. If replacing an active gateway, the owner explicitly targets it. The old gateway remains active while the replacement awaits confirmation; owner confirmation atomically revokes the old gateway and activates the new one, without two active gateways. Old records remain attributed to the old gateway. Any old unsynchronized backlog stays on the old Pi and needs a separately authorized recovery path; it must not be silently relabeled as new-gateway data. Revocation stops new cloud sync and commands, but does not claim to stop local physical activity.

## 4. Planned Pi, Mosquitto, and MariaDB changes

### Pi services and configuration

- Extend `pi5/dashboard/dashboard.py` with a local setup login, pairing form and status view. Set a strong dashboard setup credential in protected Pi configuration during installation; do not reuse MQTT, gateway, database or Supabase credentials. Require that local session for both `POST /api/setup/pair` and `GET /api/setup/gateway`; validate same-origin/CSRF token and code format on writes, and rate-limit attempts. Restrict the service to the trusted branch LAN with a host firewall; never expose port 5000 publicly. The present HTTP dashboard cannot protect the code or local login from an untrusted LAN, so document that prototype constraint and require reviewed HTTPS before wider use. Serve the sustained dashboard with a production WSGI server rather than Flask's built-in development server, following [Flask deployment guidance](https://flask.palletsprojects.com/en/stable/deploying/).
- The local pairing handler accepts only the one-time code from the browser. Server-side Pi logic validates the configured HTTPS API base and TLS, creates/loads the protected gateway identity and secret, submits the claim and persists its pending/active status. `GET /api/setup/gateway` returns the non-secret pairing state, fingerprint and branch display/ID after a verified cloud response, never a credential or raw code. An existing binding refuses a conflicting claim unless an explicit reviewed replacement/reset procedure is underway. The Pi dashboard does not access Supabase directly.
- Add a local MQTT client-provisioning command or equivalent reviewed Mosquitto administration procedure. Issue a unique credential for each project-owned ESP32/simulator, restrict its publish topic to its source ID, and configure that credential on the client before first publish. Rotate/revoke it locally when a device is retired. Do not infer a publisher's broker username from Paho's ordinary subscriber callback. Vendor credentials/topics need their own adapter and authorization review.
- Replace `SPINSENSE_BRANCH_ID` and shared default gateway-token behavior in `pi5/ingestion_worker.py` and `pi5/sync_worker.py` with the local paired gateway configuration. The Pi may use the branch UUID to construct project-owned MQTT topics, but the cloud ignores any client-supplied branch for authorization.
- Ingestion subscribes to the project-owned ESP32/simulator topics under the paired branch, with a stable authenticated MQTT client identity. It validates envelopes and source attribution, records source/quality/receipt metadata, and writes the observation and any local condition event in one MariaDB transaction. Use persistent `(device_id, boot_id, sequence)` uniqueness where supplied; do not add a message to a volatile dedup cache before a successful commit or treat identical sensor values at different times as one observation. The current firmware's QoS 0 publish does not become reliable because ingestion subscribes at QoS 1; document gaps before local commit. Unregistered but attributable clients create/update a pending discovery; their samples remain diagnostic, not approved operational evidence. Messages received before confirmed pairing may remain locally identifiable but must not be silently reattributed to the new branch or used as current operational state.
- Sync selects bounded, ordered pending rows; sends versioned batches using the gateway credential and explicit IDs; and sets `is_synced=1` plus `cloud_acknowledged_at` only for IDs named in a successful **committed** cloud response. Remove the current fallback from missing `accepted_ids` to the entire batch; missing/malformed acknowledgements leave rows pending. Permanently invalid/conflicting rows are quarantined with a reason; temporary failures back off. Replay cannot replace newer current state. An empty batch/heartbeat updates gateway contact without manufacturing a sensor reading. Poll approved configuration and command state through authenticated outbound HTTPS.
- Configure Mosquitto with no anonymous production listener, one credential per project-owned node/simulator and least-privilege topic permissions. Bind the intended listener to the Pi AP address, not `0.0.0.0`, and update the local worker's broker address/authentication consistently; verify AP startup ordering and that the listener is not reachable on `wlan1`. Protect broker configuration and local credential files, enable broker persistence where required, and verify service restart behavior. The broker enforces which client may publish a source topic; the subscriber validates that topic and its payload. The vendor `server/...` namespace must be handled by an isolated, verified adapter; it is not rewritten into the project namespace by assumption.

### ESP32 publisher readiness

- Keep `device_id` stable through reconnects and add a new boot/session identifier on restart with a monotonic sequence within that session. The current random MQTT client-ID suffix is not a durable identity; broker credentials and permitted topic must bind the device to its published source. A missing device clock remains explicitly uncertain, while gateway receipt time is recorded separately.
- Encode missing/invalid DHT22, gas and weight values as unavailable with quality metadata, never as a physical zero. Preserve each sensor's actual sample time when a cached value is republished. The existing five-second MQTT publish period and PubSubClient QoS 0 behavior require measured latency and gap evaluation against the PRD; do not claim every pre-ingestion physical sample survives disconnects. Check the MQTT topic plus payload against the installed client's packet limit after adding identity/quality fields.

### MariaDB migration plan

Inspect the actual `edge_iot` schema, row counts, MariaDB session time zone, installed pruning job and free disk space; back up committed rows and prove restore on an isolated copy before migration. Prepare additive, staged DDL with a forward and restore/recovery procedure. MariaDB `CREATE TABLE` and `ALTER TABLE` cause implicit commits, so do not present the schema migration as one rollbackable transaction. Keep DML observation/outbox writes transactional. [MariaDB DDL behavior](https://mariadb.com/docs/server/reference/sql-statements/transactions/sql-statements-that-cause-an-implicit-commit); [TIMESTAMP session time-zone conversion](https://mariadb.com/docs/server/reference/data-types/date-and-time-data-types/timestamp).

| Table/change | Minimum planned fields and constraints |
|---|---|
| `gateway_configuration` | Single local gateway UUID, cloud branch UUID only after a verified claim response, claim ID, configuration revision, pending/confirmed/expired/revoked status and timestamps; credential remains in a protected file. Reject multiple active identities on one installation. A claimed branch ID is not locally authoritative before cloud confirmation. |
| `device_registry` | Local source/client identity, cloud device UUID, type, source kind, approval state, config revision, first/last seen. Unique source identity within the gateway. |
| `device_discoveries` | Stable candidate ID, source/client identity, proposed type, first/last seen, sample evidence/quality, upload state and decision; one pending candidate per identity. |
| `sensor_telemetry` additive columns | `record_id`, `gateway_id`, source/client ID, boot/session ID, sequence, gateway receipt time, source-time quality, source kind, validation/quality metadata, sync state, cloud acknowledgement time and rejection reason; indexes for `(is_synced, id)`, `(gateway_id, record_id)`, durable source deduplication and device/time lookup. Retain raw payload and existing local IDs; record the session time zone used to interpret legacy `TIMESTAMP` values. |
| `sync_attempts` or equivalent durable outbox metadata | Batch/request ID, attempted IDs, attempt/result times and retry state where needed for restart diagnosis. A response loss must not advance local record status. |

Legacy rows that lack verified gateway/device identity remain marked `legacy_unattributed`. They are not automatically assigned to the newly paired branch or exposed as physical branch readings. Preserve them for local diagnosis or a separately reviewed backfill with provenance. The historical guide's pruning job relies on a sync flag that the current worker can set without an explicit cloud acknowledgement and on source `recorded_at`; it is not a safe retention gate. Suspend it before migration or worker cutover, then replace it only after committed-ID and `cloud_acknowledged_at` semantics, backup/restore and storage-pressure behavior are tested. Never purge unsynced, quarantined or unattributed evidence automatically.

## 5. Planned FastAPI, Supabase, and API contracts

First inspect migration state and the Render revision. Prepare a new reviewed Supabase PostgreSQL migration after the existing onboarding/branch migrations for `gateway_claims`, `gateways`, `devices`, `device_discoveries`, `telemetry_observations`, and `latest_device_state` (or equivalently named projections). Include organization/branch foreign keys, one-active-gateway-per-branch and unique-device/source constraints, credential verifiers, claim `issued`/`redeemed_pending`/`confirmed`/`expired`/`cancelled` states, at most one unconfirmed claim per branch, redemption/confirmation deadlines, verification fingerprint, actor/timestamps, observation replay keys, and indexes for pending claims/discoveries and branch/device/time reads. Keep branch `service_status` separate from hardware setup state; no gateway claim opens a branch. Enable RLS and revoke direct `anon`/`authenticated` writes on exposed tables; FastAPI must check the current owner/membership/branch state before elevated operations. The live application of migration `003_personnel_roles.sql` and any later schema is unverified. See [Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).

The routes below are **proposed contracts**, not currently working endpoints. FastAPI supplies Pydantic/OpenAPI schemas; TypeScript models must match them. Every owner route verifies a current active owner in the branch's organization. Assigned managers may read non-secret gateway/device health for their branch; specialists see only their permitted machine or LPG domain. No public response exposes gateway IDs used for authentication, local broker addressing, raw environmental readings, or credentials.

| Route | Caller and request | Response and rule |
|---|---|---|
| Existing `POST /branches` | Owner bearer token; stable `{request_id, branch details, primary_manager_user_id}`. | Commit branch and assignment once; return `{branch: {id, service_status: "closed", ...}}`. The web action must retain that ID and continue to resumable hardware setup; a retry reuses the request ID. Pairing failure never rolls back branch creation. |
| `POST /branches/{branch_id}/gateway-claims` | Owner bearer token; `{request_id, replace_gateway_id?}`. | `{claim_id, code, expires_at}` once; repeat `request_id` cannot mint another claim. An active gateway requires explicit replacement target. Code never appears in subsequent status/list responses. |
| `GET /branches/{branch_id}/gateway-claims` | Own-organization owner bearer token. | Current unconfirmed claim ID/status/deadlines and pending gateway fingerprint if redeemed, never the code or credential; lets a reload resume setup without browser storage. No claim returns an empty current-claim result. |
| `GET /branches/{branch_id}/gateway-claims/{claim_id}` | Own-organization owner bearer token. | `{claim_id, status, expires_at, confirmation_expires_at?, gateway_id?, verification_fingerprint?}`; fingerprint appears only after redemption, never the code or credential. Supports polling and resume. Foreign branch/claim IDs are denied. |
| `POST /branches/{branch_id}/gateway-claims/{claim_id}/cancel` | Own-organization owner bearer token. | Cancels an issued or redeemed-pending claim, invalidates its code/pending credential and records actor/time. Idempotent on repeat; cannot cancel an active confirmed gateway. An old active gateway targeted for replacement remains active. |
| `POST /branches/{branch_id}/gateway-claims/{claim_id}/confirm` | Own-organization owner bearer token; `{gateway_id}` after visual fingerprint comparison. | Transactionally check pending state, identity and deadline, then activate one gateway and close any explicitly targeted old binding. Same confirmed claim/gateway retry is idempotent; mismatched identity, expired claim, inactive owner/organization or another active gateway conflicts. Record confirming actor/time. |
| `GET /branches/{branch_id}/gateways` | Owner or assigned manager. | Active/history status, last contact, last valid observation, and replacement state, with no secret or claim code. |
| `POST /edge/claim` | One-time code plus `{gateway_id, credential}` over HTTPS; no operator token. | Atomically consume the code and create one inactive pending binding; return `{claim_id, gateway_id, organization_id, branch_id, status: "awaiting_confirmation", verification_fingerprint, confirmation_expires_at}`. Same gateway/secret retry returns that pending state; a different identity or replayed code conflicts. Store only the credential verifier. |
| `GET /edge/claim-status` | Pi-held gateway bearer credential. | `{claim_id, gateway_id, status, organization_id?, branch_id?, verification_fingerprint?, confirmation_expires_at?, config_revision?}` for pending/active/expired/revoked recovery, including a lost `POST /edge/claim` response. A pending credential can read only its own claim state, never configuration, observations or commands. |
| `GET /edge/config` | Active gateway bearer credential. | Credential-derived branch and approved device registry/configuration revision. A revoked gateway receives no config or commands. No Supabase administrative key. |
| `POST /edge/discoveries` | Active gateway; stable candidate IDs, MQTT client/source identities, first/last seen, proposed kind and evidence quality. | Idempotent accepted candidate IDs; untrusted or conflicting identities rejected. Candidate data is not an operational reading. |
| `GET /branches/{branch_id}/device-discoveries`; `POST /branches/{branch_id}/device-discoveries/{candidate_id}/approve` | Owner; approval body `{device_type, label, source_kind, capacity_kg?}` plus supported capability/position mapping as applicable. | Candidate and registered device IDs, status and revision. Verify candidate belongs to the branch gateway; type/capability fields are validated. Duplicate approval is idempotent or explicit conflict, never a duplicate asset. |
| `POST /branches/{branch_id}/devices/{device_id}/retire`; `POST /branches/{branch_id}/gateways/{gateway_id}/revoke` | Owner, explicit target. | Recorded retirement/revocation and no further operational grant. Preserve history; require a new claim for replacement. |
| `POST /edge/sync` | Active gateway; `{schema_version, gateway_id, batch_id, records, heartbeat}` with record IDs and quality/ordering envelope. | `{accepted_ids, rejected: [{record_id, reason, retryable}], config_revision}` only after database commit. A committed identical retry is acknowledged; a foreign or different-payload collision is rejected. Empty records update contact only. |
| Existing branch machine/LPG reads | Authenticated, current role/branch/domain check. | Persisted, attributed assets and latest valid/stale state. Empty, pending, disconnected and provider failure remain distinct; no default in-memory fleet or cylinder reading. |

For cloud latest state, a historical replay may be stored but cannot overwrite a newer accepted observation. Pending gateway/discovery data cannot create public availability, valid fuel levels, or a physical incident. Approval affects future commissioned readings; earlier pending samples remain diagnostic and do not retroactively trigger incidents. Configuration and command delivery follow the PRD's separate expiry/evidence rules; this onboarding slice does not claim real vendor command support.

## 8. Open implementation checks and exclusions

- **Unverified live facts:** actual Pi AP address/NAT/firewall, broker/dashboard listeners and systemd units, MariaDB table/time zone/root cron/disk capacity, deployed worker and flashed ESP32 revisions, Render deployment revision and environment, Supabase migration `003` status, vendor JSON examples/credentials and machine access. The historical guide cannot establish these. These checks precede migrations or deployment.
- **Explicitly later:** QR pairing or remote access to the Pi dashboard, automatic activation of unknown devices, a second physical Pi, cloud MQTT, mandatory WebSockets, real vendor commands, payments and physical automatic gas shutoff. The existing [vendor questions](VENDOR_MQTT_REQUIREMENTS.md) remain the evidence checklist for the adapter.
- **Prototype LAN limit:** The existing Pi dashboard uses HTTP. Treat its setup UI as usable only on a trusted, restricted branch LAN; the code and local login are not confidential against an attacker on that network. Require reviewed HTTPS and local-dashboard exposure controls before use on untrusted networks. A public cloud page must not fetch or embed the local HTTP dashboard.
- **Security boundary:** no hard-coded secrets, anonymous production MQTT, trust in payload branch IDs, direct browser writes to gateway tables, replay-based current-state regression, or claim that MQTT broker ACK proves machine execution.

This document is a plan. Applying database migrations, changing the Pi, deploying Render, and connecting live hardware require their own implementation and verification steps.
